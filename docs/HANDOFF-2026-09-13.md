Written 2026-09-13 at the end of the build sessions. This is the document to read before touching anything. It records what exists, why it is shaped the way it is, how it was built, and what to check before making changes. Companion documents: `docs/infra/gcp-2026-09-13.md` (Google Cloud), `docs/infra/cloudflare-2026-09-13.md` (Cloudflare), `SPEC.md` (behavioural contract), `DESIGN_PLAN.md` (UI spec), `IMPLEMENTATION_PLAN.md` (phase 2 plan, historical), `docs/claude_memory/` (decision notes), `src/components/ui/README.md` (UI primitives and their traps).

## 1. What DriveDash is

A mobile-first PWA that wraps the signed-in user's own Google Drive:

- **Shelves** (home): pinned files grouped into user-named shelves with an icon and colour. Tiles, not rows. Tap opens the file in Drive, long-press or the dots button opens the action sheet.
- **Search** (bottom-nav tab): full-screen search over the whole Drive with type chips, recent searches, swipe-right-to-pin and swipe-left-to-share on result rows, name matches ranked first.
- **Action sheet**: Open, Pin/Unpin, Get link, For client, Download, Download as PDF, Send by email, Set label, Move to group. Every share flow ends on a result view with Share… (Web Share API), WhatsApp (on touch devices) and Copy.
- **Share links with expiry** (1 / 3 / 7 days / none). Email shares use Drive's native `expirationTime`. Anyone-links are revoked by an **on-open sweep** (no cron, by decision). Every share is logged in a per-user ledger with Revoke and Extend.
- **Copy for a client**: copies the file into `Client Shares/<Client>/` in the user's Drive and shares the copy, so the original stays untouched.
- **Onboarding**: 4-step spotlight tour, offer card on first sign-in with an empty hot list, "Show me around" in the Menu, empty states, first-time swipe hint, toggletips.
- **Access**: open signup for any verified Google account up to `MAX_USERS` (30) seats; admins (`ADMIN_EMAILS`) bypass the cap and can Block / Remove users at `/admin/users`.
- **Install hint** for the PWA and a **Delete my data** flow that removes everything the app holds for a user.
- Public pages: landing at `/about` (signed-out `/` redirects there), `/login`, `/privacy`, `/terms`.

Live at **https://drivedash.shubhammathur.in**. Repo: `mathurshubham/drivedash` on GitHub, default branch `main`.

## 4. Hard rules (enforced by tests — do not weaken without updating the guard)

1. **Never delete user data.** `src/lib/__tests__/drive.test.ts` walks `src/lib` and `src/app/api` and asserts exactly two Drive `DELETE` call sites: `revokePermission` in `shares.ts` (URL contains `/permissions/`, id from our ledger) and `deleteAppDataFiles` in `appdata.ts` (files found by name in `spaces=appDataFolder`). No `trashed: true`, no `emptyTrash`, `drive.ts` has zero DELETEs. Files and folders the user owns are never deleted or trashed.
2. **Own Drive only.** Every `files.list` uses `corpora=user` and `'me' in owners`, except appDataFolder lookups (`spaces=appDataFolder`).
3. **Access token never reaches the browser.** API routes decode the session JWT server-side (`getSessionToken`), refresh with an in-isolate cache (`token.ts`), and pass the token to Drive.
4. **Every `/api/*` route returns `401 { error: 'unauthorized' }` without a session**; admin routes `403 forbidden` for non-admins; `requireToken` returns `403 { error: 'full' | 'blocked' }` when the registry denies. `routes.test.ts` sweeps all of them.
5. **Escape user text in Drive `q` strings** (`escapeQ`).
6. **No cron, no stored refresh token server-side.** The user chose on-open sweep over a scheduled job to avoid a standing Google credential on Cloudflare.

| Method | Path | Auth | Purpose |
|---|---|---|---|

| GET | `/api/files/[id]/download?format=native\|pdf` | token | streamed download / export |
| POST | `/api/files/[id]/share` | token | anyone or email share with expiry; logs a ledger entry |
| POST | `/api/files/[id]/copy` | token | copy into `Client Shares/<Client>/`, share the copy |
| GET/PUT | `/api/hotlist` | token | shelves JSON (PUT merges `settings.clientSharesFolderId`) |
| GET | `/api/shares` | token | share ledger |
| POST | `/api/shares/sweep` | token | revoke expired anyone-links (client calls once per open, 10-min throttle) |
| DELETE/PATCH | `/api/shares/[shareId]` | token | revoke now / extend 7 days |
| GET | `/api/access/me` | session | `{ email, allowed, isAdmin, reason?, maxUsers }` |
| GET | `/api/admin/users` | admin | registry + KV budget snapshot |
| POST | `/api/admin/users/[email]/block` | admin | `{ blocked }` |
| DELETE | `/api/admin/users/[email]` | admin | remove (only when blocked) |
| DELETE | `/api/account` | session (no cap check) | revoke app-created shares → delete appData files → remove registry record → revoke Google tokens; returns `{ steps }` |
| * | `/api/auth/[...nextauth]` | — | Auth.js |

## 6. Access model

- Google's gate: the OAuth app is **published (In production), unverified**. Any Google account can consent; each sees "Google hasn't verified this app" once (Advanced → Go to DriveDash). Hard Google limit: **100 users lifetime** for unverified restricted-scope apps. Not seeking verification (would need CASA, about $540/year).
- Our gate: `resolveAccess(email)` in `access.ts`. Admins always pass. Others are registered into KV `users` on first sign-in if the non-admin count is under `MAX_USERS`; otherwise `reason: 'full'`. Blocked users get `reason: 'blocked'`. Denied users land on `/access-denied?reason=…` and can still use Delete my data.
- Concurrency: `mutateUsers` re-reads before writing and retries up to 3 times; last-writer-wins is accepted at ~30 users.
- KV writes: registration (≤30 lifetime), `lastSeenAt` refresh at most once per user per 24h, admin actions. `kv-budget.ts` skips optional writes past 200/day per isolate and 503s essential ones past 500.

## 7. How it was built (process worth repeating)

1. Discussion before code: product shape, hosting, scopes, sharing semantics, cap policy were all agreed in chat first. `SPEC.md`, then `IMPLEMENTATION_PLAN.md`, then `DESIGN_PLAN.md` captured the contracts.
2. Parallel agents in git worktrees, each on its own branch with a strict file-ownership list; a coordinator merged them (`merge --no-ff`), ran gates, and resolved conflicts (usually "both sides added", keep both).
3. Adversarial reviews with throwaway probes before each merge; findings fixed on the branch, then re-verified.
4. UI acceptance: a Sonnet agent drove Chrome at phone width and saved screenshots; the coordinator judged them and dispatched fix rounds. Real-device screenshots from the user drove two polish rounds.
5. Merges to `main` are always merge commits (no squash), then `pnpm run deploy`, then a production smoke (`/` → `/about` 307, `/login` 200, `/api/search` 401).
6. Memory notes in `docs/claude_memory/` record decisions and traps that are not derivable from code.

Merged PRs, in order: #1 branding pages, #2 access requests (later replaced), #3 share expiry + log, #4 open signup + cap + KV budget, #5 UI redesign, #6 phone polish, #7 share result view + sheet snap + tour nav, #8 README, #9 install hint + delete my data.

## 8. Traps that cost time (read `src/components/ui/README.md` for the full list)

- `motion` features load lazily: an `m.*` element with a hiding `initial` can stay invisible. Use CSS keyframes for anything eagerly rendered.
- A page-transition `transform` creates a stacking context and becomes the containing block for `position: fixed` children. Overlays (tour, offer cards, toggletips) must portal to `body`.
- `vaul` converts snap points against `window.innerHeight` and never measures the panel; the panel must be full-height, snap points are fractions.
- `sonner` 2 pauses toast timers while the tab is hidden or hovered; the adapter adds a hard dismiss ceiling.
- `Pressable` base classes include `relative`; a child needing `absolute` must be wrapped.
- Auth.js lazy config: `auth(handler)` resolves asynchronously, so `proxy.ts` awaits it. `auth()` with no args is fine in server components.
- Next dev loads `.dev.vars` over `.env.local`.
- `Intl` date formatting differs between Node and Chrome → hydration mismatch; `greeting.ts` formats by hand and gates on mount.
- Bottom nav hide-on-scroll needs "never hide on short pages" and idle/route-change reveals, or it vanishes for good.

## 9. Current state and known gaps

State (2026-09-13): `main` clean, 358 tests green, deployed version `84b00f68…` on Cloudflare. Three merged legacy branches still exist on origin (`feat/access-requests`, `feat/branding-pages`, `feat/share-expiry`); safe to delete.

Not verified on a real device: dark mode parity (only code-audited), reduced motion, iOS Safari share sheet and clipboard, install prompt on Android. Verified on Android Chrome by the owner: home, tour, sheets, sharing.

Known gaps / ideas, none blocking:
- Copy-for-client takes 10–16 s (several sequential Drive calls); could parallelise folder lookup and metadata.
- Search relevance is client-ranked only (name matches first); Drive `fullText` still returns noise.
- Sweep only runs when someone opens the app; a link can outlive its expiry until then (by decision; cron would need a stored refresh token).
- No offline mode / service worker; no push.
- `/about` became dynamic (reads `searchParams` for the deleted banner). Could move the banner client-side to restore static prerender.
- Admin "Users" page is admin-only and untested on a phone.

## 10. Operating checklist

Before changing code: read §4, run `pnpm build && pnpm typecheck && pnpm lint && pnpm test`.
Before deploying: Node 22 via fnm, `pnpm run deploy`, then the smoke curls in `docs/infra/cloudflare-2026-09-13.md`.
Adding a user-visible Drive operation: never add a DELETE; extend the guard test if you must touch permissions or appData.
Adding a secret: `wrangler secret put NAME` (Node 22) and mirror it in `.env.local` and `.dev.vars`; document it in `docs/infra/cloudflare-2026-09-13.md`.
Changing OAuth scopes, redirect URIs, or the app name: `docs/infra/gcp-2026-09-13.md` lists the console pages; scope changes force every user to re-consent.
